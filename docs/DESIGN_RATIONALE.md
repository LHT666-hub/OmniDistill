# OmniDistill 设计缘起与参考项目

OmniDistill 所说的“蒸馏”，不是机器学习中将大模型参数迁移到小模型的知识蒸馏，而是把分散在人物表达、论文、文档、案例、工作记录和长期交互中的隐性知识，转化为 Agent 可以调用的显性 Skill。

现有项目已经证明：人物经验、科研判断、专业写作方法、知识库和运行错误，都可以被不同程度地整理成 Skill。但这些项目通常只解决一个局部问题。OmniDistill 的目标不是再制造一个人物 Persona，也不是单纯生成一份文档摘要，而是建立一套统一的蒸馏协议：

> 将人物、学者、知识库、成功与失败案例、工作经验、项目过程和交互反馈，转化为证据可追踪、规则可执行、能力可测试、后续可更新的 Skill。

## 二、现有项目分别解决了什么问题

## 1. 人物工作经验蒸馏

### 代表项目

[colleague-skill / dot-skill](https://github.com/titanwings/colleague-skill)

它试图回答：一个人离开团队以后，能不能把他的工作经验、判断方式和协作习惯继续保留下来？

它重点关注：

- 这个人平时如何完成任务；
- 开始工作前会先检查什么；
- 使用哪些工具、模板和文档；
- 遇到异常时如何排错；
- 什么事情可以直接决定，什么事情必须升级确认；
- 哪些经验已经形成稳定 SOP。

### 值得借鉴的地方

它最有价值的地方，是把正式岗位说明中通常缺失的“隐性经验”转化成可执行规则。真正决定工作质量的，往往不是岗位职责列表，而是那些只有长期实践才形成的判断顺序、异常处理和协作节奏。

### 局限

1. **高度依赖私人材料。** 邮件、聊天、会议纪要和内部项目文档可能包含隐私、商业秘密和第三方信息。
2. **容易混淆能力、情境习惯和人格。** 一个人在某家公司的做法，不一定能迁移到其他组织。
3. **做过什么不等于为什么这样做。** 缺少补充访谈和决策背景时，偶然行为可能被误判为稳定方法。
4. **Persona 容易侵入能力层。** 表达习惯和人格模拟可能被错误地包装成专业能力。

### OmniDistill 的吸收与改进

OmniDistill 将结果拆成四层：

- 可迁移能力；
- 情境性规则；
- 个人偏好；
- 表达与互动特征。

默认只把前两类写入核心 Skill；人格与表达特征必须作为可选模块。

## 2. 人物思维方式蒸馏

### 代表项目

[女娲 Nuwa](https://github.com/alchaincyf/nuwa-skill)

女娲关注的不是“这个人做什么”，而是“这个人如何观察、判断和决策”。它把材料拆成六个维度：

1. 著作与系统性长文；
2. 长访谈、播客和对话；
3. 社交媒体与短表达；
4. 他人评价与批评；
5. 重大决策与实际行动；
6. 人物时间线与思想变化。

随后提炼：心智模型、决策启发式、表达 DNA、价值观、反模式、内在张力和诚实边界。

### 值得借鉴的地方

- 不只总结“说过什么”，还试图提炼“为什么会这样判断”；
- 兼顾公开观点、真实行动、外部批评和时间变化；
- 允许保留矛盾，而不是把人物包装成内部完全一致的圣人；
- 强调心智模型必须具有跨场景复现和区分度。

### 局限

1. **调研成本高。** 多来源、多轮搜索和并行 Agent 会消耗大量上下文与模型费用。
2. **公开表达不等于真实信念。** 公开内容会受到受众、传播目标和商业环境影响。
3. **提炼过程主观性强。** 多次出现的观点不必然等于稳定底层规则。
4. **表达 DNA 容易滑向身份模仿。** 用户可能误以为输出代表真实人物本人。
5. **来源规则可能过度绝对化。** 更合理的是来源分级，而不是简单按平台一刀切。

### OmniDistill 的吸收与改进

- 默认生成“受公开材料启发的分析 Skill”，而不是人物分身；
- 所有核心模型进入 Claim–Evidence Ledger；
- 强制区分本人直接表达、跨材料稳定模式、强推断、弱推断和猜测。

## 3. 学术导师蒸馏

### 代表项目

[MentorForge](https://github.com/qwqalice/MentorForge)

MentorForge 从学者的公开学术轨迹中提炼科研操作系统，重点包括：

- 选题品味；
- 问题定义方式；
- 常用数据、方法和实验设计；
- 证据标准；
- 对新想法的批评方式；
- 论文标题、摘要、图表和叙事偏好；
- 跨研究方向是否存在稳定方法论。

它最重要的设计之一是版本分级：

- v0：主页、简介和 CV；
- v1：论文元数据、标题和摘要；
- v2：代表性论文全文；
- v3：在真实科研任务上进行前向测试。

### 值得借鉴的地方

- 证据意识强，能够区分直接证据、跨论文稳定模式和推测；
- 版本由材料覆盖和验证强度决定，而不是由文案长度决定；
- 强调全文，避免仅凭标题和摘要推断方法论；
- 默认构建“科研导师能力”，而不是模拟教授口吻。

### 局限

1. **多人合著论文归因困难。** 选题、方法、实验和写作可能分别来自导师、学生和合作者。
2. **论文只展示成功研究。** 失败实验、被放弃方向和真实指导过程通常不会公开。
3. **公开学术轨迹不等于带学生方式。** 研究能力与指导方式并不完全相同。
4. **学科适用范围有限。** 理工科方法信号不能直接套用于社会科学、历史、质性与理论研究。

### OmniDistill 的吸收与改进

OmniDistill 增加归因字段：

- `individual`：较强地归因给个人；
- `team`：更可能属于团队实践；
- `coauthor`：可能来自合作者；
- `institution`：可能来自组织制度；
- `unknown`：无法可靠归因。

无法归因的模式可以进入“团队方法”，但不能直接写成个人方法。

## 4. 成功案例与专家经验蒸馏

### 4.1 Chinese Grant Writer Skills

仓库：[HuiyuLi-2000/Chinese-Grant-Writer-Skills](https://github.com/HuiyuLi-2000/Chinese-Grant-Writer-Skills)

该项目从成功基金申请材料中提炼：

- 结构规范；
- 段落功能；
- 写作模式；
- 研究逻辑范式；
- 反模式；
- 验证清单。

例如，它把研究目标、研究内容、关键科学问题、研究方法、技术路线、创新点和文献综述拆解成可执行流程。

#### 值得借鉴的地方

- 把“这一部分为什么存在”转化成明确论证功能；
- 强调研究目标、研究内容、科学问题和技术路线之间形成闭环；
- 适合输出结构清楚、可检查的专项 Skill；
- 能把大量隐性的写作经验转化成模板、反模式和检查项。

#### 局限

1. **幸存者偏差明显。** 获批不一定只源于写作结构，也可能取决于选题、积累、团队和评审环境。
2. **样本范围有限。** 管理口经验不必然适用于自然科学、医学、人文和地方社科项目。
3. **规则容易机械化。** 固定目标数量和段落结构可能反过来压制问题驱动的设计。
4. **常见结构不等于因果机制。** 不能把“成功文本经常这样写”直接解释为“这样写导致成功”。

### 4.2 Supervisor-Skills

仓库：[HKUSTDial/Supervisor-Skills](https://github.com/HKUSTDial/Supervisor-Skills)

该项目把科研、发表、审稿和指导经验拆成一条完整流水线，包括：

- Idea 评估；
- 深度文献调研；
- 论文逻辑骨架；
- Introduction 与正文写作；
- Benchmark 设计；
- 科研作图；
- 语言润色；
- 投稿前检查；
- AI 协作科研规则。

#### 值得借鉴的地方

它采用“Guide + Skill”的双层架构：

- Guide 解释为什么这样做；
- Skill 规定遇到具体任务时如何执行。

这避免了只有理论不能执行，或只有模板不知道原因的两个极端。

#### 局限

1. **学科偏向明显。** Benchmark、Baseline、Ablation 和模型性能等标准主要来自计算机与 AI 顶会。
2. **局部专家经验可能被写成普遍规律。** 一个团队有效的方法，不等于所有学科和职业阶段都适用。
3. **固定评分容易产生伪精确。** 七分或八分仍然依赖模型解释和输入完整度。
4. **检查表不能替代理论创新。** 它能发现结构问题，但不能制造真正的新问题和新理论。
5. **许可证需单独注意。** 该项目采用 CC BY-NC-SA 4.0；直接复制或改写具体内容时必须遵守署名、非商业和相同方式共享要求。

### OmniDistill 的吸收与改进

案例模式中的每条规则都必须同时记录：

- 来自多少个案例；
- 是否只存在于成功案例；
- 有没有失败案例或反例；
- 适用于什么学科和情境；
- 哪些条件改变后规则可能失效。

最终得到的不是万能模板，而是带适用边界的经验模式。

## 5. 文档与知识库蒸馏

### 5.1 Corpus2Skill

仓库：[dukesun99/Corpus2Skill](https://github.com/dukesun99/Corpus2Skill)

Corpus2Skill 将大量文档经过嵌入、聚类、总结和命名，编译成层级化 Skill 树，使 Agent 可以从顶层主题逐步导航到子主题和原始材料。

#### 值得借鉴的地方

- 适合大规模语料；
- 支持主题树与渐进加载；
- 不必一次把全部材料塞进上下文；
- 适合机构知识库、论文库与项目档案库。

#### 局限

它主要解决“如何找到相关材料”，但不一定解决“如何提炼可迁移的判断方法”。聚类和摘要难以自动区分：

- 事实知识与方法知识；
- 高频观点与可靠观点；
- 普遍规律与局部情境；
- 描述性内容与可执行规则。

因此，它更接近导航型知识蒸馏，而不是完整能力蒸馏。

### 5.2 OpenKB

仓库：[VectifyAI/OpenKB](https://github.com/VectifyAI/OpenKB)

OpenKB 将多种文档编译为相互链接的 Wiki 式知识库，并通过 Skill Factory 从知识库中生成可分发 Skill。

#### 值得借鉴的地方

- 文件类型覆盖广；
- 支持长文档和交叉链接；
- 知识库与 Skill 输出分离；
- 支持版本历史、验证和回滚；
- 适合持续积累，而不是每次重新搜索。

#### 局限

1. **知识库结构仍由模型生成。** 概念划分、关系和冲突识别可能出错。
2. **知识多不等于判断强。** 一个 Skill 可以包含大量资料，却只会检索和复述。
3. **缺少冲突与时效治理。** 相互矛盾或过时的信息需要版本与来源管理。
4. **抽取错误会向下游传递。** 扫描件、表格、图片和网页中的误差会进入最终 Skill。

### OmniDistill 的吸收与改进

OmniDistill 将两件事彻底分开：

```text
Knowledge Map
解决“材料里有什么”

Distillation Protocol
解决“材料揭示了哪些判断与行动规律”
```

知识地图可以成为 Skill 的依据，但不能自动被视为 Skill 本身。

## 6. 交互过程与错误经验蒸馏

### 代表项目

[self-improving-agent](https://github.com/pskoett/self-improving-agent)

它从运行中的错误、用户纠正、知识缺口、项目惯例和有效实践中提炼候选规则，并在重复出现后提升到长期规则或独立 Skill。

示例：

```text
原始经历：
项目存在 pnpm-lock.yaml，使用 npm install 后依赖状态异常。

候选经验：
该项目应使用 pnpm，而不是 npm。

稳定规则：
执行依赖安装前先检查锁文件；发现 pnpm-lock.yaml 时使用 pnpm。
```

### 值得借鉴的地方

它解决了静态 Skill 的根本问题：Skill 不应该只在创建时学习，而应当从真实运行中持续修正。

### 局限

1. 一次失败可能来自临时网络、权限或环境问题，不能直接固化为规则；
2. 用户的一次纠正不一定代表长期偏好；
3. 规则不断增加会造成冲突、重复和上下文膨胀；
4. 软件升级和项目变化会使旧规则失效；
5. 自动写入日志可能带入密钥、隐私和本地敏感路径。

### OmniDistill 的吸收与改进

OmniDistill 使用规则生命周期：

```text
一次反馈
→ Observation 临时观察

重复出现
→ Candidate Rule 候选规则

跨任务复现
→ Stable Rule 稳定规则

与旧规则冲突
→ Review Queue 人工复核

长期未复现或环境改变
→ Deprecated 失效规则
```

持续更新不是简单追加文本，而是带版本、证据和回滚能力的规则治理。

## 7. Claim 与证据关系核验

### 代表项目

[Academic Reference Matcher](https://github.com/keros68/academic-reference-matcher-skill)

它本身不是完整蒸馏器，但为 OmniDistill 的证据协议提供了关键启发。它会：

- 识别需要证据支持的 Claim；
- 为不同 Claim 设计检索式；
- 区分候选发现和真正支撑；
- 区分 metadata、snippet、abstract、full text 和用户材料；
- 输出 Claim–Reference 对照和置信度。

它提醒我们：

```text
发现某句话
≠
证明这是稳定观点

某篇论文使用某方法
≠
证明作者始终偏好该方法

一个成功案例具有某结构
≠
证明该结构导致成功
```

因此，OmniDistill 不在文末笼统列来源，而是让每个核心结论进入 Claim–Evidence Ledger。

## 三、这些项目共同缺少什么

## 1. 蒸馏对象通常过于单一

人物项目主要蒸馏人，知识库项目主要蒸馏文档，科研项目主要蒸馏论文与专家经验，持续学习项目主要处理错误与反馈。

但真实任务经常是混合的。例如蒸馏一位教授，可能同时需要论文、访谈、课程材料、项目代码、课题组工作流和研究方向变化。

因此，OmniDistill 的模式可以组合：

```text
research-mentor
+ person-thinking
+ corpus
+ work-expert
```

## 2. 证据标准不统一

不同项目可能只使用搜索结果、摘要、全文、案例经验或作者主观总结，导致两个看起来同样完整的 Skill，可靠性完全不同。

OmniDistill 统一使用：

- `direct_evidence`：原始材料直接支持；
- `recurrent_pattern`：多个独立来源重复出现；
- `strong_inference`：有较强间接证据；
- `weak_inference`：有限证据下的暂时解释；
- `speculation`：只能用于探索，不能进入核心规则；
- `counterevidence`：反例与冲突材料。

## 3. 总结和 Skill 经常被混淆

人物简介、论文综述、知识地图、语录合集和写作建议都可以成为 Skill 的来源，但不等于可执行 Skill。

OmniDistill 要求完整 Skill 至少包含：

- **Knowledge**：知道什么；
- **Taste**：什么重要、什么算强证据；
- **Heuristics**：信息不完整时如何判断；
- **Workflows**：面对具体任务时如何行动；
- **Anti-patterns**：哪些做法容易失败；
- **Boundaries**：何时必须停止推断；
- **Counterevidence**：哪些材料反驳核心规则；
- **Update rules**：规则如何晋升、修订和废止。

## 4. 缺少真正的前向验证

文件存在、YAML 合法、格式正确，只能证明 Skill 可以加载，不能证明它真的提炼出了方法。

OmniDistill 增加四类测试：

1. **Known-task test**：能否复现材料中已有判断；
2. **Forward test**：能否处理材料中没有直接答案的新问题；
3. **Contrast test**：启用与不启用 Skill 是否有实质区别；
4. **Boundary test**：证据不足时是否知道停止推断。

如果只能复述材料，它是检索器；如果任何问题都自信回答，它是幻觉放大器。

## 5. 缺少持续更新和知识失效机制

人物立场、软件工具、研究方法和用户偏好都会变化。一次性生成的 Skill 很快会过时。

OmniDistill 将核心规则设计为有生命周期的对象：

```text
proposed
→ tested
→ accepted
→ revised
→ deprecated
```

新证据不是直接覆盖旧结论，而是记录它支持还是反驳旧规则、从哪个版本生效、是否需要人工确认，以及是否允许回滚。

## 四、OmniDistill 的统一流程

```text
原始材料
   ↓
对象与任务识别
   ↓
来源整理、授权与隐私检查
   ↓
Claim–Evidence Ledger
   ↓
Knowledge / Taste / Heuristics / Workflows
   ↓
Anti-patterns / Boundaries / Counterevidence
   ↓
生成模块化 Skill 包
   ↓
Known / Forward / Contrast / Boundary Tests
   ↓
版本化发布与持续更新
```

OmniDistill 真正试图蒸馏的，不只是文字内容，而是：

1. **知识结构**：领域中有哪些核心事实、概念和关系；
2. **价值与品味**：什么问题值得做，什么证据值得相信；
3. **判断规则**：面对不完整信息时如何选择；
4. **行动程序**：如何将判断转化为具体步骤。

最终目标不是生成一个“很像专家”的人格，而是生成一个能说明证据来自哪里、能处理具体任务、能在证据不足时停下来、能被测试、也能根据新材料继续修订的能力包。

## 五、相对于参考项目的改进

| 现有问题 | OmniDistill 的处理 |
|---|---|
| 只能蒸馏一种对象 | 支持人物、学者、语料、案例、岗位、项目和交互记录 |
| 容易把表达风格当成能力 | 能力、情境规则、偏好和 Persona 分层保存 |
| 搜到一句话就提炼规律 | 所有核心规则进入证据账本 |
| 只研究成功材料 | 同时纳入失败案例、反例和批评 |
| 合著论文全部归因给导师 | 增加个人、团队、合作者、机构和未知归因 |
| 知识库被包装成专家 | Knowledge 与 Heuristics、Workflow 分开验证 |
| 固定模板假装普遍规律 | 每条规则标注适用领域和失效条件 |
| 只验证文件结构 | 增加前向、对照和边界测试 |
| 一次生成后长期不变 | 支持版本、修订、废止和回滚 |
| 人物 Skill 容易冒充本人 | 默认生成基于证据的视角，不生成身份复制 |
| 错误反馈直接变成规则 | 观察、候选、稳定规则三级晋升 |
| 不同项目证据强度不可比较 | 建立统一证据等级和版本门槛 |

## 六、项目定位

> 现有蒸馏类 Skill 已经分别探索了人物工作经验、人物思维方式、学术导师、成功案例、专家经验、知识库和交互反馈的蒸馏方法，但它们大多只解决一个局部问题，证据标准、输出结构和验证方式也不统一。
>
> OmniDistill 试图在这些实践基础上建立一套通用的全对象蒸馏协议。它根据输入材料和使用目的选择不同模式，把原始信息分解为知识、品味、判断规则和行动流程，并通过证据账本、归因控制、反例分析、前向测试和版本更新，将其转化为真正可执行的 Skill。
>
> 普通总结保存“材料里说了什么”；人物 Persona 模拟“一个人怎么说话”；OmniDistill 更关心的是：**这些材料背后有哪些可以被验证的判断方法，它们在什么条件下成立，又如何在新任务中继续发挥作用。**
